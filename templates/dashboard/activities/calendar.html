Above the cap the grid keeps its own height and the space below it is page, not an empty card - which is what was wrong with it before. 64rem is comfortably above the grid's natural height, so the cap only ever limits growth; it never squeezes the rows. {% endcomment %}

{% comment %} ---- The day dialog ------------------------------------------------------ Clicking a day opens this: what is already on that day, and a short form to put something new on it. Adding is the thing people come to a calendar to do, so the form is the point of the dialog and the existing activities are the context that makes it safe to fill in - you can see the clash before you create it. The form is the real Django form, posted to the ordinary create URL with `quick=1`. Nothing here is a shortcut past a permission: the view applies the same ownership rules to this post as to the full page, and if the post fails validation the full page renders with the errors on it. Layout: exactly one thing scrolls. The heading and the buttons are pinned, and the middle is the only scroll container, so Save is reachable without scrolling to find it. The height cap lives on the wrapper rather than on the , and the flex column with it: an author `display:flex` on a dialog beats the browser's own `dialog:not([open]) { display: none }` - author styles outrank the user-agent sheet whatever the specificity - and the dialog would then be on screen permanently, open or not. Opened by scripting only. Without it, the day cell is a plain link to the day beside the grid, and "Add Activity" at the top of the page still works. -------------------------------------------------------------------------- {% endcomment %}
